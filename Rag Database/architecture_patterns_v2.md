## Structural

### Modular Monolith
**Problem:** A team wants the clean module boundaries and independent-evolution benefits often associated with microservices, but cannot yet afford the operational cost of a distributed system, and does not yet know where the correct service boundaries lie.

**Solution mechanics:** A modular monolith ships as a single deployable unit (one process, one build artifact) but is internally partitioned into well-defined modules organized around business capabilities / bounded contexts. Enforcement is at the *code* level, not the network level: modules expose explicit public interfaces and hide internals; cross-module calls are in-process method calls, so there is no serialization, network latency, or partial-failure handling. Data is logically partitioned — each module owns its tables/schema and other modules access that data only through the owning module's API, not by direct SQL joins across ownership boundaries. Boundary enforcement can be automated with build-time tooling (package-visibility rules, ArchUnit-style dependency tests, language module systems, separate compilation units) that fails the build when an illegal dependency is introduced. Because everything runs in one process, a single ACID transaction can still span modules, and refactoring across boundaries is cheap.

**Use when:** Starting a new application where the domain is not yet well understood (Fowler's MonolithFirst); small-to-medium team; strong consistency across the domain is required and eventual consistency would be an unwarranted burden; you want the option to later extract microservices at known-stable seams. Fowler: *"you should build a new application as a monolith initially, even if you think it's likely that it will benefit from a microservices architecture later on."*

**AVOID when:** Multiple teams need to deploy independently on separate cadences (a single deploy pipeline serializes them); parts of the system have radically different scaling profiles that must scale independently at the process level; you need technology heterogeneity (different languages/runtimes per component). The dominant failure mode is boundary erosion — without disciplined enforcement, modules leak into each other and you get a "Big Ball of Mud" that is monolith-shaped but not modular. Do NOT treat "modular monolith" as a synonym for "we'll clean it up later"; the modularity must be actively enforced or it decays.

**Trade-offs:** You keep single-process simplicity (one deploy, in-process calls, ACID transactions, trivial local debugging) at the cost of coarse-grained scaling (you scale the whole process even if only one module is hot) and a single shared failure/deployment domain (one bad deploy takes down everything). A well-built modular monolith is the cheapest path to later microservices; a poorly-modularized one cannot be decomposed — Fowler notes attempts to break up tangled monoliths "quickly ended up in a mess."

**Relation to other patterns:** Composes with Layered architecture inside each module. It is the recommended precursor/alternative to Microservices (MonolithFirst). It nominally uses one physical database but should still enforce logical schema-per-module ownership to preserve future extractability. Directly opposed to the Shared Database anti-pattern within its own walls.

**Sources:** Martin Fowler, "MonolithFirst" and "Microservice Premium" (martinfowler.com); Sam Newman, *Building Microservices* 2nd ed.; Azure Architecture Center, "Architecture styles."

### Microservices
**Problem:** A large, complex system built and operated by many teams needs independent deployability, team autonomy, independent scaling, and technology diversity that a single monolithic deployment cannot provide.

**Solution mechanics:** The application is decomposed into a suite of small, independently deployable services, each owning a single business capability within a bounded context, each running in its own process, communicating over lightweight mechanisms (typically HTTP/REST or asynchronous messaging). The defining mechanics: (1) each service is independently deployable via automated pipelines; (2) each service privately owns its data (Database per Service) — no shared database; (3) decentralized governance lets each team choose its own stack; (4) an orchestration platform (e.g., Kubernetes) schedules, scales, and recovers services; (5) an API gateway fronts external clients; (6) observability (centralized logging, distributed tracing, metrics) is mandatory because a request now traverses many processes. Module boundaries are enforced *physically*: because a service is reachable only over the network through its API, illegal cross-boundary access is structurally prevented.

**Use when:** The system is genuinely too complex/large to manage as a monolith; many teams need to work and deploy independently (Conway's Law / Inverse Conway Maneuver); components have divergent scaling needs; you can afford mature DevOps, automated deployment, and monitoring. Fowler: *"don't even consider microservices unless you have a system that's too complex to manage as a monolith."*

**AVOID when:** The system is simple or new and boundaries are not yet stable — starting greenfield with microservices is the classic mistake (*"Almost all the cases where I've heard of a system that was built as a microservice system from scratch, it has ended up in serious trouble."*). Avoid when the team is small or lacks DevOps maturity; when strong cross-entity ACID consistency is a hard requirement (distributed transactions force eventual consistency and Sagas); when the domain is poorly understood (wrong boundaries are extremely expensive to move — "refactoring in the large becomes much harder"). Anti-patterns: the **distributed monolith** (services that must deploy in lockstep — tight design-time coupling); **nano-services** (boundaries so fine that most developer time goes to inter-service plumbing); **shared database** across services.

**Trade-offs:** You gain strong module boundaries, independent deployability, and independent scalability; you pay the "Microservice Premium" — distribution (remote calls are slow and can fail), eventual consistency, and operational complexity requiring a mature ops team. Fowler documents a case where microservices were a net negative in staff-hours even though the architecture helped absorb a rapid influx of developers.

**Relation to other patterns:** Requires Database per Service, API Gateway, and typically Saga (distributed transactions), Circuit Breaker, Retry, and Event-Driven/Async Messaging for decoupling. It is the alternative to the Modular Monolith and Layered/N-Tier styles. It conflicts with the Shared Database anti-pattern (which destroys autonomy) and with synchronous request/response chains deep enough to create tight runtime coupling.

**Sources:** Fowler & Lewis, "Microservices" (2014); Fowler, "Microservice Trade-Offs," "Microservice Premium" (martinfowler.com); Chris Richardson, microservices.io ("Microservice Architecture" pattern); AWS "Microservices on AWS" whitepaper; Azure Architecture Center, "Microservices architecture style."

### Layered / N-Tier Architecture
**Problem:** An application needs a clear separation of technical responsibilities (presentation, business logic, data access) so that concerns are decoupled and the codebase is understandable and maintainable.

**Solution mechanics:** The application is divided into horizontal logical layers — commonly presentation, business logic, and data access — where each layer has a defined responsibility and a layer may only call into the layer directly below it (strict/closed layering). "N-tier" adds *physical* separation: layers become deployable tiers (web tier, business tier, data tier) that run on separate machines and communicate over the network, often with a load balancer between tiers. Azure's reference deployment shows internet → load balancer → web-tier VMs → load balancer → business-tier VMs → load balancer → data tier (primary/secondary SQL). Tiers create boundaries for scalability, reliability, and security; you can scale or secure tiers independently and use layer-7 routing to direct traffic to specific tiers.

**Use when:** Traditional enterprise applications; migrating an existing on-premises app to cloud with minimal refactoring ("lift and shift"); requirements are still evolving; hybrid on-prem/cloud topologies; teams want an easy-to-understand structure. Portable across cloud and on-premises.

**AVOID when:** You need high release velocity and independent deployability of features — horizontal layering means a change to one layer can cascade across layers, and the whole app usually deploys together. Avoid a middle tier that only performs trivial CRUD pass-through (Azure: it "adds latency and complexity without delivering meaningful value"). Avoid when the domain is complex and you want capability-aligned teams (layers cut *across* capabilities, not along them). Failure mode: layers become large and monolithic, reducing update frequency and limiting innovation; without discipline the system devolves into a big ball of mud.

**Trade-offs:** You gain conceptual simplicity, separation of concerns, portability, and independent tier scaling/securing; you pay in change amplification (cascading changes across layers), potential added latency per tier hop, and a tendency toward monolithic deployment. Horizontal layering can also encourage a database-centric design where business logic thins out.

**Relation to other patterns:** Composes naturally inside a Modular Monolith or inside each Microservice. It is the classic alternative to Microservices and Web-Queue-Worker styles. Fowler's PresentationDomainDataLayering describes the logical layering variant. Pure horizontal layering conflicts with capability-oriented (vertical) decomposition favored by microservices and DDD.

**Sources:** Azure Architecture Center, "N-tier architecture style" and "Architecture styles"; Martin Fowler, "PresentationDomainDataLayering."

## Communication

### Synchronous Request/Response (REST over HTTP)
**Problem:** A client needs an immediate, correlated answer to a specific request — a low-latency, in-band result it will act on right away.

**Solution mechanics:** The caller issues an HTTP request (GET/POST/PUT/DELETE against resource URIs) and blocks awaiting the response, which carries the result and a status code. REST conventions: resources identified by URIs; standard verbs with defined semantics (GET safe/idempotent; PUT/DELETE idempotent; POST not); stateless interactions (each request carries all context; no server-side session affinity); representations (usually JSON) in the body. Correlation is implicit — the response returns on the same connection. Because calls are blocking, callers must set per-attempt timeouts and overall deadlines, and typically wrap remote calls with Retry and Circuit Breaker to survive transient faults. Idempotency keys make non-idempotent operations safely retryable.

**Use when:** The caller genuinely needs the result before proceeding (reads, queries, interactive UI actions); the operation is fast and the downstream is highly available; simple point-to-point integration; you want the simplest possible mental model and easy debugging.

**AVOID when:** The work is long-running or resource-intensive (blocks the caller and threads); the caller does not actually need an immediate result (use async messaging); you would create deep synchronous call chains across services — this produces tight runtime coupling where "service X cannot respond to a request until another service Y has responded," multiplying latency and reducing availability (a downstream outage cascades upstream). Avoid synchronous fan-out to many services for one request without aggregation. Avoid retrying synchronous calls without backoff+jitter and circuit breakers — retry storms cause cascading failure.

**Trade-offs:** You gain simplicity, immediate results, and easy reasoning/debugging; you pay with temporal coupling (both parties must be up simultaneously), reduced availability (product of the chain's availabilities), and susceptibility to cascading failure and latency amplification in deep chains. Self-contained services can mitigate by returning `202 Accepted` and completing asynchronously.

**Relation to other patterns:** Fronted by API Gateway and Load Balancing; hardened by Circuit Breaker and Retry with Backoff. It is the alternative to Asynchronous Messaging and Event-Driven Architecture. It conflicts with strict loose-coupling goals when chained deeply; microservices.io recommends replacing tight synchronous chains with Sagas or command-side replicas to reduce runtime coupling.

**Sources:** microservices.io (runtime-coupling articles; "A phone company's customer experience: tight runtime coupling"); Azure Architecture Center (Asynchronous Request-Reply, messaging guidance); Google SRE, "Addressing Cascading Failures."

### Asynchronous Messaging / Queue-Based Load Leveling
**Problem:** A producer generates work faster or more unevenly than a downstream service can process it, and intermittent load spikes overwhelm the downstream, causing timeouts, throttling, or failures.

**Solution mechanics:** A message queue is introduced as a buffer between producer and consumer. The producer writes a message to the queue and returns immediately; one or more consumers pull messages at their own sustainable rate. The queue decouples the two in time (temporal decoupling — they need not run simultaneously) and in throughput (producer can burst; consumer drains steadily). Reliability mechanics: messages persist until acknowledged, so a downstream outage does not lose work (messages wait and are processed on recovery). Delivery is typically at-least-once, so consumers must be **idempotent**. Visibility/lock mechanisms (e.g., Azure Service Bus PeekLock: the message is hidden while a consumer processes it; `Complete` on success, `Abandon` on failure makes it visible again) prevent double-processing and enable redelivery. Dead-letter queues capture poison messages. Scaling the consumer pool (Competing Consumers) increases drain rate.

**Use when:** Workload has intermittent spikes that can overwhelm downstream services; you need to decouple request intake from processing throughput for resilience and cost control (provision consumers for *average*, not peak, load); tasks can be processed asynchronously; you need to protect a fragile or rate-limited downstream.

**AVOID when:** The caller requires a low-latency synchronous response (the queue adds latency and a one-way hop; you'd need a separate reply channel); workload volume is predictably low and stable, so queueing adds complexity with little benefit; strict end-to-end ordering is required (a queue with parallel consumers does not preserve submission order — you need sessions/partitions, which constrain scaling). Key anti-pattern: autoscaling consumers without bounding their aggregate downstream rate merely "moves the overload to downstream dependencies" (Azure).

**Trade-offs:** You gain load leveling, resilience to downstream outages, independent scaling, and cost efficiency (average-load provisioning); you pay with added latency, eventual/async semantics, the need for idempotent consumers and poison-message handling, and loss of strict ordering unless you add sessions. Queues are one-way; request/reply needs extra machinery.

**Relation to other patterns:** Combines with Competing Consumers (scale the drain), Throttling, and Event-Driven Architecture. It is the async alternative to Synchronous Request/Response. It underpins Saga choreography and the Transactional Outbox. It conflicts with use cases needing synchronous low-latency replies or global ordering guarantees.

**Sources:** Azure Architecture Center, "Queue-Based Load Leveling," "Competing Consumers," "Asynchronous messaging options"; Azure Service Bus documentation (PeekLock, dead-letter).

### Event-Driven Architecture / Publisher-Subscriber
**Problem:** Components need to react to things that happen elsewhere without the source knowing who consumes the information, so new consumers can be added without changing the producer (dependency inversion / loose coupling).

**Solution mechanics:** A source emits events (records that "something happened") to a broker (topic/event bus). Subscribers register interest and each receives a copy of relevant events (Pub/Sub: all subscribers get every message they subscribe to — distinct from Competing Consumers, where one consumer gets each message). The producer does not call consumers and does not care about responses; the dependency is *reversed* (consumers depend on the event stream, not the producer's API). Fowler distinguishes four meanings often conflated under "event-driven": (1) **Event Notification** — thin events signaling a change, consumers call back for details; reverses dependencies but yields "no statement of overall behavior"; (2) **Event-Carried State Transfer** — events carry all data consumers need, so consumers keep local replicas and need not call back (improves availability but replicates data and introduces eventual consistency); (3) **Event Sourcing** — the event log is the system of record and state is rebuilt by replay; (4) **CQRS** — separate read/write models. Brokers provide subscription filtering; delivery is pull (poll) or proxied push.

**Use when:** You want to broadcast changes to multiple, independently evolving consumers; you want to add functionality by tapping an existing event stream without touching producers; reactive/near-real-time workflows; decoupling teams and systems. Well-suited to domains where events are already first-class (order created, payment processed).

**AVOID when:** You need a synchronous response to the publisher (pub/sub is one-way; use request-reply); consumers must process messages in a strict, guaranteed order across subscribers (pub/sub generally does not guarantee cross-subscriber ordering); you need a single atomic transaction across publisher and consumers (pub/sub is inherently async and eventually consistent — use a DB transaction or Saga); near-real-time interaction is required and broker latency is unacceptable. The central dark side is "the inability to see what's going on in the system as a whole" — no explicit statement of overall behavior, making debugging hard. Event Sourcing specifically adds significant complexity (event-schema evolution, replay with external side-effects) and is frequently over-applied.

**Trade-offs:** You gain decoupling (identity and temporal), extensibility (add consumers freely), and scalability; you pay with loss of an explicit control flow, harder end-to-end debugging, eventual consistency, and (for state transfer) data duplication. Event-carried state transfer trades more storage/replication for higher availability and lower coupling.

**Relation to other patterns:** Built on Async Messaging brokers; composes with CQRS and Saga (choreography). Distinct from Competing Consumers (load distribution) though both use queues/topics. It is an alternative to synchronous orchestration. Over-combining Event Sourcing + CQRS + microservices is a common over-engineering trap.

**Sources:** Martin Fowler, "What do you mean by 'Event-Driven'?" / "The Many Meanings of Event-Driven Architecture" (GOTO 2017); Azure Architecture Center, "Publisher-Subscriber pattern"; Azure Service Bus topics/subscriptions.

### API Gateway
**Problem:** External clients need a single, stable entry point into a microservices system; without one, clients must know and call many services directly, handle cross-cutting concerns themselves, and break whenever the backend topology changes.

**Solution mechanics:** A gateway service sits between clients and backend services as the single entry point (analogous to the Facade pattern). Core responsibilities: (1) **request routing** — map incoming requests to the right backend; (2) **API composition/aggregation** — fan out to multiple services and merge responses so a client makes one round-trip instead of many; (3) **protocol translation** — e.g., expose HTTP/JSON externally while calling gRPC internally; (4) **edge/cross-cutting functions** — authentication (often via OAuth 2.0 / OpenID Connect, validating JWTs and forwarding tokens), rate limiting, TLS termination, caching, logging. It shields clients from backend refactoring. The **Backends-for-Frontends (BFF)** variant deploys a separate gateway per client type (web, iOS, Android, third-party) so each API is tailored and one client's needs don't bloat a shared gateway.

**Use when:** A microservices system has multiple external client types; you want to centralize authentication and other cross-cutting concerns; clients (especially mobile) benefit from aggregation and reduced round-trips; you want to decouple client contracts from backend service boundaries.

**AVOID when:** You have a monolith or only a handful of services with a single client — the gateway adds a hop and operational burden for little benefit. Critical anti-pattern: letting business logic accrete in the gateway until it becomes a monolithic chokepoint ("keep it light; don't turn it into a monolith"). It is a single point of failure if not made highly available/replicated, and it adds latency to every request. A shared gateway serving many divergent clients can become bloated — that's when to switch to BFF.

**Trade-offs:** You gain a stable client contract, centralized security, fewer client round-trips, and backend encapsulation; you pay with an extra network hop (latency), an operational component that must be scaled and made HA, potential to become a development bottleneck, and the risk of becoming a distributed monolith's chokepoint.

**Relation to other patterns:** Essential companion to Microservices; composes with Load Balancing, Circuit Breaker, Retry, and Rate Limiting/Throttling; BFF is its per-client variant. It is where an LLM/Model Gateway conceptually sits for AI traffic. It should not absorb domain logic (conflicts with keeping services authoritative for their capabilities).

**Sources:** Chris Richardson, microservices.io ("API Gateway / Backends for Frontends"; authentication articles); Azure Architecture Center (gateway patterns); AWS "Microservices on AWS."

## Data

### Cache-Aside (Lazy Loading)
**Problem:** Reading data directly from the primary data store on every request is too slow or too costly, and the cache technology in use does not natively provide read-through/write-through, so the application must manage the cache itself.

**Solution mechanics:** The *application* code, not the cache, owns population and invalidation. Read path: (1) attempt to read the item from the cache by key; (2) on a **cache miss**, read from the data store; (3) write the retrieved item into the cache (with a TTL) and return it — so subsequent reads for that key are served from cache. Hot data lazily rises into the cache on demand without pre-loading everything. Write path: write to the data store, then **invalidate** (delete) the corresponding cache entry; the next read repopulates it with fresh data. Key considerations: TTL/expiration matched to how often data changes (too short defeats the cache, too long serves stale data); eviction policy when full; guarding against **cache stampedes** (many concurrent misses on the same key) with locks; optionally caching null results; using a shared/distributed cache (e.g., Redis) so multiple app instances see consistent cached data.

**Use when:** Read-heavy workloads with data read far more often than written (product catalogs, user profiles, config); resource demand is unpredictable (loads on demand, no assumption about which data is needed); the cache lacks native read-through/write-through; you can tolerate slightly stale data between a write and its invalidation.

**AVOID when:** The cached dataset is static and small — instead prime the cache at startup and disable expiration (lazy loading adds a needless first-request penalty). Avoid caching web-farm session state in a way that introduces client-server affinity (use a shared session store). Avoid when the application cannot tolerate any staleness — cache-aside "doesn't guarantee consistency between the data store and the cache"; an external process can change the store and the cache won't know until reload. Local in-memory cache-aside across multiple instances yields divergent copies (inconsistency) — use a distributed cache. Failure mode: updating the store without invalidating produces a stale cache; a mis-ordered update/invalidate under concurrency can re-cache stale data.

**Trade-offs:** You gain lower read latency, reduced load on the data store, and full application control over what is cached; you pay with application complexity (you own population/invalidation and stampede handling), inevitable best-effort/eventual consistency, and a cold-start miss penalty. Cache-aside is easier to reason about than write-behind because the cache is a passive read layer.

**Relation to other patterns:** An alternative to read-through/write-through/write-behind caching (where the cache manages the store). Composes with Materialized View and the read side of CQRS. Often paired with a distributed cache backing stateless services (session offload). Main tension is with strong-consistency requirements.

**Sources:** Azure Architecture Center, "Cache-Aside pattern"; AWS ElastiCache / Reliable Web App guidance (distributed cache for session/state offload).

### Command Query Responsibility Segregation (CQRS)
**Problem:** In complex domains, using a single model for both updates and reads produces a model that does neither well; read and write workloads have different shapes, scaling needs, and consistency requirements.

**Solution mechanics:** CQRS splits the conceptual model into two: a **Command** model handling state changes (create/update/delete) and a **Query** model handling reads, raising Bertrand Meyer's Command-Query Separation to the architectural level (Greg Young). At minimum it is "the creation of two objects where there was previously only one." In the fuller form, the two use separate data models, often separate stores: the command side processes commands and emits changes; the query side serves reads from one or more **materialized views** physically optimized for queries. The read store is updated from the write store, frequently asynchronously (e.g., by subscribing to events the write side publishes), which makes the read side **eventually consistent** with the write side. This lets reads and writes scale independently (e.g., many read replicas) and each model be optimized for its job. Often (but not necessarily) combined with Event Sourcing.

**Use when:** Collaborative domains with high contention where many users read/write the same data; read and write workloads must scale independently (read-heavy systems); complex domains where a unified model is unwieldy; you need task-based UIs or specialized read projections. Often applied only to a subset (bounded context), not the whole application.

**AVOID when:** The domain fits a simple CRUD mental model — "for most systems CQRS adds risky complexity" (Fowler). Fowler warns: "beware that it is difficult to use well and you can easily chop off important bits if you mishandle it," and he has "seen cases where it's made a significant drag on productivity, adding an unwarranted amount of risk." Avoid applying CQRS across an entire application (it makes the whole architecture complex). Avoid when the team cannot handle eventual consistency between models. Common anti-pattern: adopting CQRS + Event Sourcing reflexively because it's fashionable.

**Trade-offs:** You gain independent read/write scaling, query-optimized read models, and a cleaner write domain model; you pay with more moving parts (two models, synchronization), eventual consistency between sides, and higher cognitive/operational overhead. The write-side model gets simpler; the system as a whole gets more complex.

**Relation to other patterns:** Frequently composes with Event Sourcing and Event-Driven Architecture (events propagate write→read). It is a way to implement queries that span microservices (materialized views fed by service events), complementing Database per Service and Saga. It is an alternative to a single CRUD model / Reporting Database (which offloads only demanding queries while keeping one main model). Do not combine with simple CRUD domains.

**Sources:** Martin Fowler, "CQRS" (martinfowler.com); Greg Young, "CQRS Documents" (cqrsinfo.com); Azure Architecture Center, "CQRS pattern" and "Architecture styles"; microservices.io (CQRS for cross-service queries).

### Database per Service
**Problem:** In a microservices architecture, if services share a database they become coupled at the data layer — schema changes ripple across services, and independent development, deployment, and scaling become impossible.

**Solution mechanics:** Each service exclusively owns its data; persistent data is accessed only through that service's API, never by another service reaching into its tables. Implementation variants (increasing isolation): private-tables-per-service, schema-per-service, and database-server-per-service (private-tables and schema-per-service have the lowest overhead). True database-per-service means separate connection strings, credentials, and lifecycle management, so a team can migrate or upgrade its database without coordinating with others. Because a single ACID transaction can no longer span services, cross-service data operations are implemented as a series of local transactions coordinated by **Sagas**, and cross-service queries use **API Composition** (the caller/gateway joins results from multiple services) or **CQRS materialized views** (a view subscribes to services' events). The **Transactional Outbox** pattern atomically updates a service's database and publishes an event.

**Use when:** You are building microservices and need loose coupling, independent deployability, and independent scaling; services have different data-storage needs (polyglot persistence — relational vs. document vs. key-value); services have different compliance/security requirements; you need granular control of scaling per data store.

**AVOID when:** You do not actually have (or want) microservices — for a monolith, one database is simpler and lets you use ordinary ACID transactions and SQL joins. Avoid if the business demands many strongly-consistent, low-latency transactions spanning what would be multiple services (the resulting Saga/eventual-consistency complexity may not be worth it — consider keeping those subdomains in one service). The dominant anti-pattern it exists to prevent is the **Shared Database**, where multiple services read/write the same tables via local ACID transactions — convenient short-term but it recreates tight coupling and "is counter to the Decentralized Data Management characteristic of microservices... without decoupling the data, the architecture is not microservices." Failure mode: implementing database-per-service but still doing cross-service joins/queries at the database level defeats the purpose.

**Trade-offs:** You gain loose coupling, independent deploy/scale, polyglot persistence, fault isolation (one DB failure doesn't sink all services), and no single-point-of-failure data layer; you pay with the inability to use cross-service ACID transactions (must use Sagas/eventual consistency), harder cross-service queries (API Composition or CQRS), and the operational burden of managing many heterogeneous databases.

**Relation to other patterns:** Requires Saga (distributed transactions), API Composition and/or CQRS (cross-service queries), and Transactional Outbox (reliable event publishing). A defining companion of Microservices. The direct opposite of the Shared Database anti-pattern. Composes with Event-Driven Architecture for data propagation.

**Sources:** Chris Richardson, microservices.io ("Database per service," "Shared database"); AWS Prescriptive Guidance, "Database-per-service pattern."

### Saga (Distributed Transaction)
**Problem:** A business operation must update data owned by multiple services (each with its own database), but distributed ACID transactions (two-phase commit) are unavailable or undesirable because they block, create single points of failure, and don't scale.

**Solution mechanics:** A saga implements a distributed operation as a sequence of **local transactions**, each in a single service that commits atomically and then triggers the next step. If any step fails, the saga executes **compensating transactions** that semantically undo the preceding committed steps (compensation, not rollback — data was already committed). Two coordination styles: (1) **Choreography** — no central coordinator; each local transaction publishes domain events that trigger the next service's local transaction; decentralized and loosely coupled, good for few steps, but the overall flow is implicit and hard to trace. (2) **Orchestration** — a central orchestrator tells each participant which local transaction to execute, tracks saga state, and drives compensations on failure; clearer flow and easier to manage for complex sagas, at the cost of a central component. Sagas require **idempotent** handlers (messages are retried), and they provide ACD but **not isolation** — intermediate states are visible to other transactions, so countermeasures (semantic locks, commutative updates) may be needed. Originates from Garcia-Molina & Salem, "Sagas" (ACM SIGMOD 1987).

**Use when:** You need to maintain data consistency across multiple services without 2PC; long-running business processes (order processing, travel booking, supply chain) that span services; you can tolerate eventual consistency and can define compensating actions.

**AVOID when:** The operation can live in a single service with a single ACID transaction (then just use the local transaction — no saga needed); you require strict isolation / strong consistency (sagas lack isolation; concurrent sagas can see intermediate state); compensating actions are impossible or unsafe to define (some real-world effects can't be cleanly undone — e.g., an email already sent). Choreography becomes an anti-pattern when the number of steps grows large (the implicit event web becomes impossible to reason about); orchestration becomes a risk if the orchestrator accretes too much business logic or becomes a single point of failure. Naive implementations that aren't idempotent double-apply on retry.

**Trade-offs:** You gain cross-service consistency without distributed locking/blocking and better availability than 2PC; you pay with eventual consistency, the design burden of writing and testing compensating transactions and failure scenarios, lack of isolation (requiring countermeasures), and a shift in design thinking. Choreography trades traceability for decoupling; orchestration trades a central component for clearer control flow.

**Relation to other patterns:** Requires Database per Service (the reason sagas exist) and builds on Compensating Transaction. Choreography uses Event-Driven Architecture / Async Messaging; orchestration often uses a workflow engine. Composes with Transactional Outbox (reliable event publishing) and CQRS (querying saga results). It is the microservices alternative to 2PC / distributed ACID transactions.

**Sources:** Garcia-Molina & Salem, "Sagas" (ACM SIGMOD 1987); Chris Richardson, microservices.io ("Saga pattern"); Azure Architecture Center, "Saga design pattern."

### Data/Model Separation (AI)
**Problem:** AI/ML systems couple a trained model (weights, architecture) with the data it operates on (training data, feature stores, retrieval corpora, prompts); conflating them makes it impossible to update knowledge without retraining, to govern data access, or to reason about provenance and freshness.

**Solution mechanics:** The system separates the **model** (a comparatively static artifact: pre-trained weights, versioned, deployed as an inference endpoint) from the **data** it uses at inference time (dynamic knowledge in external stores — vector databases, document stores, feature stores, databases). Instead of baking knowledge into weights via training, current knowledge is injected at request time (e.g., RAG retrieves relevant fragments and includes them in the prompt; feature stores serve fresh features). This yields independent lifecycles: knowledge can be refreshed by changing the data store — AWS Prescriptive Guidance states RAG can incorporate the latest documents "in a few minutes," while fine-tuning "can take a few hours to days" and is not ideal for frequently-changing documents. Enforcement includes versioning models and datasets independently, and applying data access controls at the data layer so the model retrieves only what the current user is permitted to see (least-privilege for RAG).

**Use when:** Knowledge changes frequently or must be cited/traceable (use external data + RAG rather than encoding it in weights); you need auditable data provenance and freshness; you must enforce per-user data access on what the model can retrieve; you want to reuse one model across many datasets or swap models without re-ingesting data.

**AVOID when:** The "separation" is taken so far that it ignores capabilities that genuinely require fine-tuning (style, format, niche terminology are better taught to the model than retrieved) — treat model and data updates as complementary, not mutually exclusive. Avoid ignoring that retrieved data becomes part of the trust boundary — unvalidated external data injected into prompts is an attack surface (prompt injection via poisoned documents). Failure mode: connecting a model to a data store for RAG without enforcing least privilege lets the model surface records the user shouldn't see — AWS guidance: "make sure that it cannot retrieve data that a given user isn't allowed to see."

**Trade-offs:** You gain independent update cadences (fast knowledge refresh vs. slow model change), auditability, access governance, and model/data reuse; you pay with the operational complexity of maintaining and securing separate data infrastructure (vector stores, feature stores), retrieval latency, and the need to secure the data→model path. A hybrid (fine-tune periodically for tone + RAG for facts) can reduce cost while keeping freshness.

**Relation to other patterns:** Foundational to RAG and the LLM/Model Gateway; complements AI Guardrails (validate retrieved data and outputs) and the Security Baseline (least privilege on retrieval). Parallels classic separation-of-concerns and Database-per-Service thinking applied to AI. Contrasts with pure fine-tuning / weight-baked-knowledge approaches.

**Sources:** AWS Prescriptive Guidance, "Retrieval Augmented Generation options" and "Comparing RAG and fine-tuning"; AWS Prescriptive Guidance, "Data security, lifecycle, and strategy for generative AI" (least-privilege on RAG data); Martin Fowler & Bharani Subramaniam, "Emerging Patterns in Building GenAI Products."

## Scalability & Resilience

### Horizontal Scaling with Stateless Services
**Problem:** A single server cannot handle growing load, and vertically scaling one big server creates "fate sharing" — its failure takes down the whole application; you need to add capacity and survive node failures.

**Solution mechanics:** The application is designed to be **stateless** — per AWS, it "does not need knowledge of previous interactions and does not store session information" locally on disk or in memory between requests. All session/user state is offloaded to an external, resilient, multi-zone store (e.g., Amazon ElastiCache/Redis, DynamoDB, or a database); anything that can be is passed in request parameters, headers, or tokens instead of stored server-side. Because no request depends on server-local state, **any** available instance can serve **any** request, so you scale out (add interchangeable instances — "scale-out") behind a load balancer, and instances can be replaced or terminated at will without availability impact. This enables autoscaling (add/remove instances on demand, distributed across Availability Zones for reliability) and serverless compute (AWS Lambda, Fargate) where any compute resource services any request.

**Use when:** Load is variable or growing; you need high availability and tolerance to individual node failure; you want elastic autoscaling and to "stop guessing capacity"; you want to use serverless or containerized compute. Especially for web/API front ends behind a load balancer.

**AVOID when:** The workload is inherently stateful in a way that cannot be externalized cheaply (e.g., long-lived in-memory sessions, certain stateful stream processors) — though most such state can be offloaded. Note that statelessness pushes state to the external store, which then must itself be scaled and made resilient (it can become the bottleneck/SPOF). Avoid relying on sticky sessions / server affinity as a substitute for externalizing state — affinity undermines even load distribution and breaks when a node dies. Anti-pattern: storing session state on local disk/memory in a horizontally scaled fleet (a crash loses the session; scaling is uneven).

**Trade-offs:** You gain elastic horizontal scaling, resilience to node loss (instances are interchangeable), and simpler failure recovery; you pay with the latency and cost of an external state store, the need to design for state offload, and shifting the scaling/HA problem onto that store. AWS rates the risk of *not* being stateless (REL05-BP06) as **Medium**.

**Relation to other patterns:** Requires Load Balancing in front and a distributed cache/store (Cache-Aside for session offload) behind. Foundational to Microservices and serverless. Composes with autoscaling and health checks. It conflicts with designs that rely on server-local session state or sticky sessions.

**Sources:** AWS Well-Architected Reliability Pillar, "REL05-BP06 Make services stateless where possible" (risk level: Medium; offload to ElastiCache/DynamoDB); AWS Architecture Blog, "Architecting for Reliable Scalability" (horizontal scaling, fate sharing, stateless scaling model).

### Load Balancing
**Problem:** Incoming traffic must be distributed across a pool of backend instances so that no single instance is overloaded while others idle, unhealthy instances are avoided, and the pool can scale and fail over transparently.

**Solution mechanics:** A load balancer sits in front of a backend pool and distributes requests according to an algorithm while continuously health-checking backends and routing only to healthy ones. **Layer-4** load balancers (e.g., AWS Network Load Balancer) operate at the transport layer (TCP/UDP/TLS), forwarding by connection — extremely high throughput, no payload awareness. **Layer-7** load balancers (e.g., AWS Application Load Balancer) operate at the application layer (HTTP/HTTPS), evaluating listener rules to route by path/host and enabling content-based routing, TLS termination, and header inspection. Distribution algorithms range from state-unaware **Round Robin** to state-aware **Least-Loaded / Least Outstanding Requests** and **Weighted Round Robin** (backends report utilization/QPS/errors, and clients weight distribution by a capability score). Health checks remove failing backends; **connection draining / deregistration delay** (AWS default 300 seconds) lets in-flight requests finish before an instance is removed; **cross-zone load balancing** spreads traffic across instances in all zones rather than only the local zone (off by default for NLB).

**Use when:** You run horizontally scaled, stateless instances; you need high availability and transparent failover; you need to scale a pool elastically; you need TLS termination or content-based routing (Layer 7) or ultra-high-throughput L4 forwarding (Layer 4).

**AVOID when (pitfalls, not "don't use"):** Naive **Round Robin is suboptimal** because it ignores that request costs vary enormously, machines are heterogeneous, and performance is affected by unpredictable neighbors — the Google SRE Book ("Load Balancing in the Datacenter") states verbatim that "Round Robin can result in a spread of up to 2x in CPU consumption from the least to the most loaded task." But smarter policies have their own failure modes: a policy routing to the backend with the fewest active requests can be fooled by a **sinkholing** unhealthy backend that fails requests very fast (fast errors look like low load, so the LB sends it *more* traffic) — the SRE-documented fix is to "count recent errors as if they were active requests." Also, each client's view of load is partial (only its own requests), so Least-Loaded across many clients can still leave a ~2x spread. Avoid load balancing without health checks (you'll route to dead backends) and without connection draining (you'll drop in-flight requests during deploys/scale-in). Avoid assuming a fallback backend is equivalent when failing over.

**Trade-offs:** You gain even distribution, HA, failover, and elastic scaling; you pay with an infrastructure component to run and make HA, added latency, and the subtlety that "smarter" algorithms require backend cooperation (reporting load) and can misbehave (sinkholing) if not carefully designed. L7 gives routing intelligence at higher per-request cost; L4 gives raw throughput with no payload awareness.

**Relation to other patterns:** Enables Horizontal Scaling with Stateless Services; sits behind/with API Gateway; composes with Health Checks, Autoscaling, Circuit Breaker, and Retry. Distinct from an API Gateway (which adds routing/aggregation/auth) though they overlap. Cross-zone LB composes with multi-AZ reliability designs.

**Sources:** Google SRE Book, Ch. 20 "Load Balancing in the Datacenter" (Round Robin up-to-2x CPU spread; Weighted Round Robin; sinkholing and the "count errors as active requests" fix; lame-duck health); AWS Elastic Load Balancing docs (Application vs. Network Load Balancer L7/L4; health checks; deregistration delay/connection draining default 300s; cross-zone load balancing).

### Circuit Breaker
**Problem:** When a remote dependency becomes slow or unresponsive, callers pile up waiting on timeouts, exhausting threads/connections and causing failures to cascade across the system.

**Solution mechanics:** The protected remote call is wrapped in a circuit breaker object that monitors failures and has three states (Nygard, popularized by Fowler): **Closed** — calls pass through; successes reset the failure count, failures increment it. When failures cross a threshold, the breaker **trips** to **Open** — all further calls fail fast immediately (return an error or fallback) without attempting the real call, so callers don't block on timeouts and the struggling dependency gets breathing room. After a configured recovery timeout, the breaker moves to **Half-Open** and allows a single trial call: success closes the breaker (recovered); failure re-opens it. Key considerations: choose which exceptions count as failures (network/timeout yes; ordinary business errors no); emit monitoring/alerts on trip; often run calls on separate threads (futures) so even the initial timeout doesn't tie up the caller; optionally provide a fallback response when open. (Common library defaults, e.g. the Python `circuitbreaker` package: open after 5 consecutive failures, 30-second recovery timeout.)

**Use when:** Calls to remote services or integration points that can fail or hang; you want to fail fast and prevent cascading failure / resource exhaustion; you want to give a failing dependency time to recover; high-traffic paths where many callers hit the same dependency.

**AVOID when:** Local, in-process calls that cannot hang on the network (a breaker adds needless complexity); operations where failing fast is worse than waiting (usually it isn't); when the "failure" is actually a normal business outcome that shouldn't trip the circuit (mis-classifying business errors causes spurious trips — a documented pitfall: a breaker opening due to a local `KeyError`/`OSError` leads to false conclusions). Avoid a breaker with no monitoring (you won't know it tripped) and no fallback where one is needed. It does not *fix* a persistently broken dependency — it only limits blast radius.

**Trade-offs:** You gain protection against cascading failure, fast failure instead of thread-exhausting waits, and automatic probing for recovery; you pay with added complexity (state, thresholds, timeouts to tune), the need for monitoring, and the risk that a mis-tuned threshold either trips too eagerly (denying service that would have succeeded) or too late (letting damage accumulate). Fallbacks improve UX but aren't always appropriate.

**Relation to other patterns:** Pairs with Retry with Exponential Backoff — retry transient faults but stop retrying (and fail fast) when the breaker opens (Azure explicitly recommends pairing them). Composes with Timeout, Bulkhead (resource isolation), and Fallback/graceful degradation. Fronts Synchronous Request/Response calls; often lives in the API Gateway or service mesh. Complements, and is distinct from, Load Balancing health checks.

**Sources:** Martin Fowler, "CircuitBreaker" (martinfowler.com); Michael Nygard, *Release It!*; Azure Architecture Center, "Circuit Breaker pattern" and pattern-pairing guidance; Google SRE, "Addressing Cascading Failures."

### Retry with Exponential Backoff
**Problem:** In distributed systems, many failures are transient (brief network blips, throttling, momentary unavailability); giving up immediately is wasteful, but retrying naively can amplify load and cause the very outage it's reacting to.

**Solution mechanics:** On a retryable failure, the caller waits and retries, increasing the delay **exponentially** between attempts (e.g., ~1s, 2s, 4s, 8s) up to a maximum backoff, with a capped number of attempts. Crucially, add **jitter** (randomness) to each delay: pure exponential backoff is deterministic, so a thousand clients that failed at the same instant will all retry at the same moments, producing synchronized spikes ("thundering herd"); jitter spreads retries across the window, turning synchronized spikes into a smooth arrival rate. Only retry **transient** errors (HTTP 429, 408, 5xx; connection resets); do **not** retry non-retryable client errors (4xx like invalid credentials/bad syntax). Honor server signals like `Retry-After`. Make operations idempotent (or attach idempotency keys) before retrying non-idempotent writes. Set per-attempt timeouts and an overall deadline. Bound total retry volume with a **retry budget**: Google SRE (Handling Overload) recommends a per-client policy where a request is retried only while the ratio of retries to requests stays below **10%**, plus a **per-request budget of up to three attempts**.

**Use when:** Transient, self-correcting faults on idempotent (or idempotency-keyed) operations; calls to services that throttle or occasionally blip; you want resilience without manual intervention. Especially RPCs and API calls over unreliable networks.

**AVOID when:** The error is non-transient/non-retryable (client errors, business rejections) — retrying wastes resources and can't succeed; the operation is not idempotent and you have no idempotency mechanism (retries cause duplicates/double-charges); a dependency is hard-down (retries just add load — a circuit breaker should stop them). The cardinal anti-patterns: **retrying without backoff** (immediate retries overwhelm a recovering service) and **retrying without jitter** (synchronized retry storms). Google SRE documents a deeply-nested architecture where three layers each retried up to 4× independently, multiplying load 4³ = **64×** exactly when the database was least able to handle it — nested/multi-layer retries compound dangerously.

**Trade-offs:** You gain automatic recovery from transient faults and higher effective reliability; you pay with added latency (waiting between attempts), risk of load amplification if misconfigured, and the requirement for idempotency. Jitter is nearly free and almost always worth it ("any jitter is dramatically better than none"). Retry budgets and caps bound the downside.

**Relation to other patterns:** Must be paired with Circuit Breaker (stop retrying when a dependency is clearly down) and with Timeouts/Deadlines. Requires idempotent consumers (shared with Async Messaging and Saga). Avoid stacking retries at multiple layers (client, gateway, service mesh) without coordination. Complements graceful degradation and load shedding.

**Sources:** Google SRE Book, "Addressing Cascading Failures," "Handling Overload" (retry budget: 10% retry-to-request ratio, per-request budget of three attempts), and "Production Services Best Practices" (randomized exponential backoff, jitter, retry amplification); Google Cloud retry-strategy docs (retry anti-patterns, retryable vs. non-retryable, `Retry-After`); Azure Architecture Center, "Retry pattern" (pair with Circuit Breaker).

## AI-Specific

### Retrieval-Augmented Generation (RAG)
**Problem:** A foundation LLM only knows what was in its training data — it is unaware of information after its training cutoff, of private/proprietary data, and of the specific context it's operating in; asked about these, it confabulates plausible but wrong answers.

**Solution mechanics:** Instead of relying on the model's parametric memory, RAG retrieves relevant documents at query time and includes them in the prompt so the model answers from supplied evidence. Ingestion (offline): source documents are chunked, each chunk is converted to a vector via an **embedding** model, and vectors are stored in a vector store. Query time (online): the user query is embedded, an approximate-nearest-neighbor (ANN) similarity search retrieves the most relevant chunks, and those chunks are inserted into the prompt as context, from which the LLM generates a grounded (ideally cited) answer. Because knowledge lives outside the model, updating it means updating the store (fast), not retraining. Basic RAG's limitations are addressed by companion patterns: **Hybrid Retriever** (combine embedding search with keyword/other search), **Query Rewriting** (generate alternative query formulations), and **Reranker** (re-rank retrieved fragments by usefulness and send only the best). Effectiveness is measured with **Evals**.

**Use when:** You need factually grounded answers from specific, proprietary, or frequently-updated documents (internal knowledge bases, product manuals, policies, contracts); answers must be citable/traceable; knowledge changes often (RAG can incorporate the latest documents "in a few minutes"). AWS Prescriptive Guidance: "If you need to build a question-answering solution that references your custom documents, we recommend that you start from a RAG-based approach."

**AVOID when:** The task needs a learned skill, style, format, or niche terminology rather than facts — that favors fine-tuning (or a hybrid); the task is pure general reasoning/summarization with no external knowledge need (direct prompting suffices). Basic RAG is "less effective for complex information retrieval tasks because of context window constraints, query ambiguity, information verification, shallow reasoning, and multi-hop query challenges" — naive single-shot retrieval underperforms on multi-hop questions (needs iterative/agentic retrieval). Failure modes: retrieving irrelevant chunks (poor chunking/embeddings) yields confidently wrong answers; retrieving data the user isn't authorized to see (missing least-privilege on the store); stuffing too many low-quality chunks (no reranker) wastes context and degrades answers. Retrieved external content is also a **prompt-injection** vector.

**Trade-offs:** You gain current, grounded, citable answers and fast knowledge updates without retraining; you pay with retrieval infrastructure (embedding model, vector store) and its maintenance, added latency per request, sensitivity to chunking/embedding/retrieval quality, and a new attack/data-governance surface. Adding hybrid retrieval, query rewriting, and reranking improves accuracy at added cost/latency.

**Relation to other patterns:** The primary realization of Data/Model Separation for LLMs. Composes with Guardrails (validate input and retrieved data, sanitize output), the LLM/Model Gateway, and the Security Baseline (least-privilege retrieval). It is the recommended alternative/first choice versus Fine-Tuning for knowledge injection; the two can be combined (e.g., RAFT). Enhanced by Hybrid Retriever, Query Rewriting, Reranker; assessed by Evals.

**Sources:** Martin Fowler & Bharani Subramaniam, "Emerging Patterns in Building GenAI Products" (RAG, Hybrid Retriever, Reranker, Query Rewriting, Guardrails); AWS Prescriptive Guidance, "Retrieval Augmented Generation options and architectures on AWS" and "Comparing RAG and fine-tuning"; Patrick Lewis, Ethan Perez, Aleksandra Piktus et al., "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks," NeurIPS 2020 (Vol. 33, pp. 9459–9474), arXiv:2005.11401.

### Online vs Batch Inference
**Problem:** Different AI workloads have fundamentally different latency, payload, and cost profiles; serving them all through one mechanism either wastes money (idle real-time endpoints) or fails requirements (batch can't answer interactively).

**Solution mechanics:** Choose the inference mode to match the workload (per AWS SageMaker's four options): **Real-time (online)** — a persistent endpoint returns predictions synchronously with millisecond latency for interactive use; supports sustained traffic and larger per-request payloads (SageMaker real-time: payloads up to 25 MB, processing "60 seconds for regular responses and 8 min for streaming responses") but you pay for provisioned capacity whether or not it's used. **Serverless** — auto-scales (including to zero when idle) for intermittent/unpredictable traffic; pay per use, no idle cost, but smaller payloads ("up to 4 MB and processing times up to 60 seconds") and cold-start latency. **Asynchronous** — you submit a request (large payload, "up to 1 GB, and processing times of up to 60 minutes"), get an ID, and poll/receive results from an output location (S3); a queue buffers spikes and the endpoint can scale to zero — sits between real-time and batch. **Batch Transform (offline)** — process an entire dataset from storage on ephemeral instances that spin up, score all data in parallel (data sharded across instances), write results, and terminate; lowest per-prediction cost for large offline jobs, but no live endpoint and high startup overhead. A common production pattern uses several together: real-time for the interactive path, batch for nightly scoring, async for heavy document/video jobs.

**Use when (online):** interactive, low-latency, sub-second requirements with sustained/predictable traffic (fraud detection, recommendations, chatbots). **Use when (serverless):** intermittent/spiky traffic where idle cost matters. **Use when (async):** large payloads or long per-request processing where immediate response isn't required. **Use when (batch):** large volumes of data available upfront, results can wait (hours), no persistent endpoint needed (nightly scoring, dataset preprocessing).

**AVOID when:** Using **batch for interactive** applications (it can't serve individual live requests — "you can't use batch transform for interactive applications"); using **real-time for sporadic** workloads (you pay for idle capacity — expensive); using real-time/serverless for **payloads or job durations that exceed their limits** (use async/batch); using batch for **tiny datasets** (job startup overhead makes it cost-ineffective). Anti-pattern: forcing one mode for all workloads. Over-provisioned always-on endpoints for low-utilization models waste money (multi-model endpoints or serverless may fit better).

**Trade-offs:** Real-time buys low latency at the cost of continuous spend; serverless buys zero idle cost at the cost of cold starts and small payloads; async buys large-payload/long-job support and scale-to-zero at the cost of non-immediate results; batch buys the lowest per-prediction cost at the cost of no interactivity and startup latency. Choice is driven by latency requirement, payload size, traffic pattern, and cost tolerance.

**Relation to other patterns:** Async/batch modes compose with Queue-Based Load Leveling and Async Messaging (buffering spikes). Real-time endpoints sit behind Load Balancing and autoscaling and benefit from stateless design. Complements the LLM/Model Gateway (which can route to different backends) and RAG (retrieval feeds either online or batch generation).

**Sources:** AWS SageMaker AI docs, "Inference options in Amazon SageMaker AI" and Model Hosting FAQs (real-time: 25 MB / 60s regular, 8 min streaming; serverless: 4 MB / 60s; asynchronous: 1 GB / 60 minutes, scale-to-zero; batch transform for offline datasets).

### LLM / Model Gateway (Router)
**Problem:** As multiple applications and teams call multiple LLM providers/models, provider API keys sprawl across services, there's no central control of cost, routing, security, or observability, and switching or failing over between models requires code changes everywhere.

**Solution mechanics:** A gateway is a centralized proxy/control plane that all LLM traffic flows through before reaching any model provider. Its mechanics: (1) **unified API** — one endpoint (often OpenAI-compatible) fronts many providers (OpenAI, Anthropic, AWS Bedrock, self-hosted), so application code is provider-agnostic and switching models needs no code change; (2) **centralized credential management** — provider keys live only in the gateway (eliminating "secret sprawl"); apps authenticate to the gateway, not to providers; (3) **routing** — static, traffic-split (A/B testing, gradual rollout), or dynamic (route cheap/simple prompts to a small model, hard prompts to a frontier model); (4) **failover/fallback chains** — reroute to a backup provider when the primary is unavailable; (5) **token-aware rate limiting and budgets** — per team/app/key, because cost scales with tokens, not request count; (6) **semantic caching** to cut redundant calls; (7) **observability** — log tokens, latency, errors, cost per caller; (8) **guardrails/policy** at the edge (PII redaction, content filters, mTLS/JWT/OIDC). In Kubernetes it runs as a Deployment behind a Service; ConfigMaps hold routing rules, Secrets hold provider keys.

**Use when:** Multiple applications or teams need shared model access with centralized routing, spend control, provider fallback, and unified logs; you need governance/compliance (audit trails, PII masking) and cost attribution; you want to A/B test models or migrate providers without touching app code.

**AVOID when:** A single prototype or single app calls a single provider — direct SDK calls are simpler and the gateway is premature operational complexity ("For a single prototype, direct SDK calls are usually simpler"). Avoid treating a generic HTTP API gateway as sufficient — it lacks token-level budgets, prompt inspection, and LLM observability. Critical caveat/failure mode: model **fallback is not like failing over between identical replicas** — different models produce different output, tool-call behavior, latency, and safety profiles, so a gateway "can make fallback mechanically easy, but it cannot guarantee semantic equivalence" (test that fallback models give acceptable answers). Anti-pattern: distributing provider API keys to application pods instead of holding them only in the gateway. A gateway also reduces app complexity while increasing platform complexity — overkill without a platform team.

**Trade-offs:** You gain provider-agnostic code, centralized security/cost/observability, easy A/B and failover, and no secret sprawl; you pay with an added hop (latency), a component to run and make HA (a chokepoint if not), platform-team overhead, and the false comfort of "easy" fallback that may not be semantically equivalent. Cost drops only if you actually configure useful policies (caching, budgets, routing).

**Relation to other patterns:** The LLM-specific specialization of the API Gateway. Composes with AI Guardrails (enforced at the gateway edge), RAG, and Online/Batch inference backends. Uses Retry, Circuit Breaker, and Load Balancing internally for provider resilience. Distinct from an MCP/tool gateway (which governs tool access during execution).

**Sources:** MLflow AI Gateway docs and articles ("AI Gateway Architecture," "The Role of API Gateway AI Services"); Envoy AI Gateway docs (aigateway.envoyproxy.io) and analysis (unified routing, failover, security, when a gateway beats direct SDK calls).

### AI Guardrails
**Problem:** LLMs are non-deterministic and "gullible" — they can be tricked by malicious prompts into leaking confidential data or producing harmful/off-brand output, and they hallucinate confident but false answers, which is a serious liability when the LLM speaks for an organization.

**Solution mechanics:** Guardrails add validation/filtering at the boundaries of the request/response flow, typically via separate checks (often separate LLM calls or classifiers) around the main model. **Input rails** inspect the user message before it reaches the LLM — jailbreak/prompt-injection detection, content moderation, PII masking, intent classification — and can reject or rewrite it. **Output rails** inspect the model's response before returning it — checking for harmful/illegal content, blocked terms, factual self-consistency (hallucination checks), and leakage of proprietary info. NVIDIA **NeMo Guardrails** implements five rail types: input, **dialog** (control conversation flow across turns via the Colang DSL), **retrieval** (filter/mask retrieved RAG chunks), **execution** (guard tool/action I/O), and output rails; it acts as a runtime proxy separating trusted instructions from untrusted user data. Implementation approaches for a given rail: LLM-based (a separate model judges), embeddings-based (similarity to known-bad patterns), and rule-based (regex/blocklists). Fowler notes guardrails "don't come for free — the extra LLM calls involve costs and increase latency."

**Use when:** User-facing agents/chatbots that communicate in natural language and take actions; systems exposed to adversarial input (prompt injection/jailbreaks); applications with compliance, safety, or brand-safety requirements; RAG systems where retrieved content or outputs must be checked; any system where hallucination or data leakage carries real liability.

**AVOID when (calibration, not "skip safety"):** Applying heavy guardrails indiscriminately where the risk is low — each rail adds latency and cost (extra LLM calls) and can produce false positives that block legitimate requests (the decision is "weighing the costs of using them versus the risk of an incident that guardrails could prevent"). Don't treat guardrails as a complete security solution: single-model guardrails are "useful local defenses" but insufficient alone — they may miss context-specific policy violations and can be bypassed; combine with least-privilege data access, input sanitization, and defense in depth. Failure modes: over-blocking (frustrating users), under-blocking (missed jailbreaks), and treating input and output rails as independent when coordinated state is needed. Guardrails also cannot fix a fundamentally unsafe action space — that needs explicit conditional logic constraining what the agent can do.

**Trade-offs:** You gain protection against prompt injection, harmful/leaky output, and (partially) hallucination, plus policy/compliance enforcement; you pay with added latency and cost per request (extra inference), setup/monitoring effort, and false-positive/negative tuning. Model-agnostic system-level rails are reusable across LLMs but add a moving part.

**Relation to other patterns:** Enforced at the LLM/Model Gateway edge; wraps RAG (retrieval rails validate chunks); composes with the Security Baseline (least privilege, input sanitization, output filtering) and Data/Model Separation. Assessed with Evals. It is a layer in defense-in-depth, not a standalone control.

**Sources:** Martin Fowler & Bharani Subramaniam, "Emerging Patterns in Building GenAI Products" (Guardrails); NVIDIA NeMo Guardrails documentation (input/dialog/retrieval/execution/output rails, Colang); AWS Prescriptive Guidance on generative-AI data security (input sanitization, output filtering, least privilege).

## Cross-Cutting Principles

### Loose Coupling
**Problem:** When software elements (classes, modules, services) are tightly coupled, a change in one forces changes in others and a failure in one degrades others, destroying independent development, deployment, availability, and team autonomy.

**Solution mechanics:** Minimize the connectedness between elements along two distinct dimensions (Richardson). **Design-time coupling** is the likelihood that two elements must change together for the same reason; you reduce it by giving each element a stable, minimal API that encapsulates its implementation (expose the least information necessary — "deep" modules with small interfaces, Ousterhout) and by packaging tightly-coupled subdomains together rather than splitting them. **Runtime coupling** is the degree to which one element's ability to respond depends on another being available *now*; a service that "cannot respond to a request until another service has responded" is tightly runtime-coupled, increasing latency and reducing availability (availability becomes the product of the chain). You reduce runtime coupling with asynchronous messaging/events (temporal decoupling), **self-contained services** (respond with a partial result — e.g., `202 Accepted` — then complete asynchronously via a Saga), command-side replicas, and event-carried state transfer (consumers keep local copies so they don't call back). Broker-based pub/sub decouples identity (broadcast without knowing consumers) and time.

**Use when:** Always a goal in multi-team or distributed systems; especially critical in microservices where tight coupling manifests as the distributed monolith (design-time) or availability cascades (runtime).

**AVOID when (nuance):** Loose coupling is a principle, not an absolute to maximize blindly — decoupling has costs. Excessive decoupling produces its own anti-patterns: event-driven flows with "no statement of overall behavior" that are hard to trace; event-carried state transfer that replicates data and forces eventual consistency; nano-services where the plumbing between too-fine elements dominates. Two subdomains that genuinely change together should be kept together (forcing a boundary between them creates lockstep changes across services — worse than one service). Don't add asynchrony/indirection where a simple in-process call suffices.

**Trade-offs:** Loose design-time coupling buys independent evolution and team autonomy at the cost of designing and maintaining stable APIs and sometimes duplicating logic. Loose runtime coupling buys higher availability and lower latency at the cost of eventual consistency, more complex clients (handling partial outcomes), and data replication. The right amount is contextual and must be balanced against **cohesion** (keep things that change together, together).

**Relation to other patterns:** Realized by Event-Driven Architecture, Async Messaging, Saga, Database per Service, API Gateway, and Circuit Breaker (isolating failure). It is the rationale behind Microservices' strong boundaries and the Modular Monolith's enforced modules. It directly opposes the Shared Database and distributed-monolith anti-patterns.

**Sources:** Chris Richardson, microservices.io (design-time vs. runtime coupling; "Designing loosely coupled services"; "launch status check" and "phone company CX" examples); Martin Fowler on event-driven trade-offs ("no statement of overall behavior").

### Security Baseline — Least Privilege + Encryption
**Problem:** Systems that grant broad permissions and leave data unencrypted have a large attack surface: a single compromised credential or intercepted/stolen data store can expose the entire system.

**Solution mechanics:** Two foundational, complementary controls, applied as part of defense in depth (AWS Well-Architected Security Pillar principle "Apply security at all layers: Apply a defense in depth approach with multiple security controls... edge of network, VPC, load balancing, every instance and compute service, operating system, application, and code"). **Least privilege (SEC03-BP02 / SEC03-BP04):** "Grant only the access that users require to perform specific actions on specific resources under specific conditions," and continuously "remove unneeded permissions and establish review processes to achieve least privilege." Reducing permissions "lessens the scope of impact should credentials be inadvertently exposed or otherwise accessed without authorization" (the blast-radius rationale). Mechanisms: fine-grained IAM policies, layered policy types ("layer different policy types to establish defense-in-depth"), group/attribute-based permissions rather than per-user grants, separation of duties, elimination of long-lived static credentials, and continuous monitoring to remove unused identities/permissions. **Encryption at rest (SEC08):** implement secure key management ("the storage, rotation, access control, and monitoring of key material"; AWS KMS uses FIPS 140-3 Level 3 validated HSMs and has "no mechanism to export AWS KMS keys in plain text") and enforce encryption so unencrypted storage is prevented. **Encryption in transit (SEC09-BP02):** "Only use protocols with encryption when transmitting sensitive data outside of your virtual private cloud" — use TLS at least 1.2 (AWS deprecated earlier TLS as of Feb 2024), preferably TLS 1.3. Both encryption best practices carry a **High** risk level if not established. These controls should be **automated** ("Automate security best practices... controls that are defined and managed as code in version-controlled templates").

**Use when:** Always — this is a baseline. Especially where sensitive/regulated data is stored or transmitted, where credentials could be exposed, and in multi-tenant or multi-service systems where blast-radius containment matters. For AI/RAG: enforce least privilege on retrieval so the model can't return data a user isn't allowed to see.

**AVOID when (pitfalls, not "skip security"):** The anti-pattern is deferring security until after scaling ("if you don't consider security properly at the initial stages, once the solution starts to scale, redesigning from scratch... is usually not a simple option"). Avoid broad wildcard permissions "to move fast," long-lived shared credentials, and unencrypted data stores/channels. Avoid treating a single control as sufficient — encryption without least privilege still lets an over-permissioned identity read decrypted data; least privilege without encryption still exposes data at rest/in transit. Note: least privilege can introduce friction (over-restriction breaks legitimate workflows), so pair it with review processes and monitoring rather than one-time lockdown.

**Trade-offs:** You gain a smaller attack surface, contained blast radius, data confidentiality even on untrusted networks, and auditability/compliance; you pay with operational effort (policy design, key management, certificate lifecycle, continuous permission review) and some developer friction. Automating the controls (policy-as-code, managed KMS/TLS) reduces ongoing cost and scales security.

**Relation to other patterns:** Enforced at the API Gateway and LLM/Model Gateway (auth, TLS termination, PII redaction), and underpins RAG / Data-Model Separation (least-privilege retrieval) and AI Guardrails (defense in depth). Composes with every other pattern as a cross-cutting concern. Opposed by convenience anti-patterns (shared credentials, unencrypted shared databases).

**Sources:** AWS Well-Architected Framework, Security Pillar — design principles ("Apply security at all layers," "Automate security best practices," "Implement a strong identity foundation," "Protect data in transit and at rest"); SEC03-BP02 "Grant least privilege access"; SEC03-BP04 "Reduce permissions continuously"; SEC08-BP01/BP02 (secure key management; enforce encryption at rest); SEC09-BP02 "Enforce encryption in transit" (TLS 1.2+; TLS 1.3 recommended); AWS Prescriptive Guidance on generative-AI data security (least privilege for RAG).
